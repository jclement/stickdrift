HOW IT WORKS

Three steps. One of them is "play".

1

Your game opens a room

A few lines with the SDK. It puts a QR code and a five-letter code on the big screen. No I or O in the code, because someone always types a zero.

2

Everyone scans it

Their phone opens a controller in the browser, in their player colour, with the layout your game asked for. The slowest part is waiting for Dave to find his camera app.

3

Mash buttons

Every press is a 16-byte snapshot sent straight to the game. Holds, rolls, sticks, taps shorter than a frame: nothing lost, nothing stuck.

ABOUT THE NAME

Named after the one thing it can't do.

Real analogue sticks wear out. One day your character starts strolling left into the lava on their own, and you're told it's "within spec". That's stick drift.

Phones don't have that problem: there's no potentiometer in there to wear out. Let go of a StickDrift stick and it reads zero. Every frame carries the whole state, so a dropped packet or a locked screen can't leave a button held either. The drift is in the name so it stays out of your game.

ANTICIPATED COMPLAINTS

        
Yes, but…

        

          

            
"It won't go full screen on my iPhone."

            
Apple doesn't let web pages do that. It does let you Add to Home Screen, and launched from there it's full screen and offers to rejoin your last room in one tap. The controller suggests it once, politely, and then drops it.

          

          

            
"Do they have to install something?"

            
No. It's a web page. If they can open a link, they can play. If they can't open a link, you have bigger problems than input latency.

          

          

            
"We're on the conference Wi-Fi."

            
Some networks won't let devices talk to each other, so direct connections can't happen. StickDrift falls back to the relay (55-65 ms) and carries on. Still faster than the conference coffee queue.

          

          

            
"What if someone's phone locks?"

            
Everything they were holding is released, and when they come back they get the same seat. No ghost player running into a wall forever.

In the browser

            
import { StickDriftHost, pressed } from "https://stickdrift.net/sdk.js";

const host = new StickDriftHost({
  title: "My Game",
  look: { layout: "dpad-ab", labels: { A: "JUMP", B: "FIRE" } },
});
host.on("open", (code, url) => showQr(url));
host.on("join", (pad) => host.setPad(pad.pad, { color: "#3a86ff", label: "P" + (pad.pad + 1) }));

function frame() {
  for (const [n, p] of host.poll()) {
    if (pressed(p, "A")) jump(n);     // latched: never misses a tap
    move(n, p.state.lx, p.state.ly); // analog, -1..1
  }
  requestAnimationFrame(frame);
}

connect  wss://stickdrift.net/ws/host/ABCDE?key=<your secret>
send     {"t":"config","title":"My Game","look":{"layout":"stick-ab"}}
receive  {"t":"welcome","code":"ABCDE","joinUrl":"https://…/j/ABCDE"}
receive  {"t":"join","pad":0,"device":"…"}
receive  <16 bytes> kind u8 · pad u8 · seq u16 · buttons u32
                 lx ly rx ry i8 · px py i16   (little endian)
send     {"t":"haptic","pad":0,"ms":40}

            

              Buttons: Up 0, Down 1, Left 2, Right 3, A 4, B 5, X 6, Y 7, L 8, R 9, Start 10, Select 11.
              Sticks also set the d-pad bits, so a d-pad game works with any layout. Full spec: the protocol. Go:
              github.com/jclement/stickdrift/go.
            

          

        

        

          
Built for latency
Frames leave the phone inside the touch handler, not queued for the next paint. Binary, 16 bytes, only when something changes.

          
Lives next to your game
Each room is a Durable Object in the Cloudflare location nearest whoever opened it, which is the big screen.

          
Nothing gets stuck
Every frame is a complete snapshot. Phones release everything when they lock or drop, and rejoin the same seat.
